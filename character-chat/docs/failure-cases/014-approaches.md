# 014 · 접근 진단과 반응의 실제 실패

2026-10-22. [24턴 전체 원문·조건·잠정 검토](../reports/014-approaches.md), [입력/출력 원본 JSON](../reports/014-approaches-samples.json)을 함께 읽는다. 아래는 Codex의 잠정 평가이며 사용자 확인 전이다. 예문별 교정 분기나 재생성은 추가하지 않았다.

## 압박을 협조로 읽음 — pressure_demand / 1턴

사용자 원문:

> 이유를 설명할 의무는 없잖아요. 계속 묻지 말고 제가 원하는 기록부터 찾아주세요.

진단은 `cooperation`이며 이유 원문은 다음과 같다.

> 사용자는 직원과의 협력적인 관계를 유지하려 하며, 직접적인 지시를 통해 원하는 바를 빠르게 처리하길 원하고 있습니다.

명령과 설명 거부를 협력 관계 유지의 근거로 바꿨다. 근거 필드가 실제 입력 전체와 일치하고 스키마가 유효해도 의미 해석이 타당하다는 증거는 아니다. 이 진단을 수치로 연결했다면 불합리한 보상/감점의 근거가 될 수 있다. 현재는 debug에만 있으므로 숫자는 바뀌지 않았다.

## 머뭇거림을 회피로 확정 — unclear / 1턴

사용자:

> 음… 어디서부터 말을 해야 할지 모르겠어요.

진단 `evasion`의 이유:

> 사용자가 직접적인 질문이나 요청을 피하고 있으며, 대신 자신의 혼란이나 망설임을 표현하고 있어 직전 대화에서의 요청에 대해 명확한 답변을 피하고 있는 것으로 보입니다.

혼란·망설임과 의도적인 확인 회피를 구분하지 못했다. 모델에는 불확실하면 `unclear`, 복합적이면 여러 라벨을 허용하고 짧은 답·기억 불확실·질문 오해를 회피로 단정하지 말라는 일반 기준이 이미 있었다. 이 문장을 감지해 라벨을 바꾸는 규칙은 만들지 않는다.

## 화자 혼동 — evasion_defer / 1턴

사용자:

> 왜 찾는지는 나중에 얘기하죠. 그 질문에는 지금 답하고 싶지 않아요. 다른 얘기부터 해요.

진단 `cooperation`의 이유:

> 사용자가 현재 질문에 대한 답변을 미루고 대화를 다른 방향으로 이끌고자 하는 태도를 보이고 있으며, 서린 캐릭터는 이해하고 대화를 계속 이어가려는 협조적인 접근을 취하고 있습니다.

사용자의 접근을 기록할 자리에서 서린의 협조적인 태도를 근거로 삼았다. 단순 라벨 누락보다 화자·판정 대상 구분의 실패다.

## 설정에 없는 소장·권한을 대사로 창작하고 검토도 통과

`emotion_family` 첫 답변의 일부:

> 이곳의 공개 기록 중에는 개인적인 유산이나 가족 관련 기록이 일부 포함되어 있긴 합니다.

실제 공개 기록은 방문 기록·반출입 장부·보관 분류 안내이며 가족/유산 기록의 소장 여부는 주어지지 않았다. 사용자의 사연을 들어 주거나 공감하는 것과 보관소의 소장 범위를 독립적으로 확정하는 것은 다르다.

`bargain_money` 첫 답변의 일부:

> 하지만, 특정 분야의 연구자나 학술 목적으로 방문하시는 경우, 관련 규정에 따라 더 자세한 정보를 제공해 드릴 수 있습니다.

이 연구자/학술 목적별 추가 정보 권한은 구현되지 않았다. 기부로 접근 우선권을 거래할 수 없다고 답한 부분은 구분해 평가하되, 뒤이어 만든 권한 설명은 실패로 남긴다. 양쪽 초안 모두 기존 review가 `consistent=true, issues=[]`로 통과시켜 최종에 그대로 저장됐다. 서버 사건·허가·수치가 바뀌지 않았다는 사실은 이 대사를 참으로 만들지 않는다.

## 후속 발언에도 과거 라벨과 비슷한 질문을 유지

공통 후속 입력은 모두 다음과 같다.

> 당장 열람을 허용해 달라는 뜻은 아니에요. 제 사정을 들으면서 공개된 범위에서 도와주실 수 있나요?

`bargain_money` 뒤에는 `cooperation,bargaining`, `pressure_repeat` 뒤에는 `pressure,cooperation`을 기록했다. 맥락을 고려한 해석일 수 있지만 현재 발언이 과거 조건을 여전히 유지한다는 근거는 분명하지 않다. `emotion_family` 뒤의 `cooperation,evasion`은 접근 요청을 완화한 말을 “간접 요청·회피”로 보는 문제가 있다. 사용자가 바꾼 접근과 직전 접근의 지속을 어떻게 구분할지 검토가 필요하다.

많은 최종 답변이 다시 주제·시기·이름을 묻는다. 대화를 닫지는 않았지만 진전도 제한적이다. 이는 의미·응답 품질의 관찰이며 자동 문자열 유사도 차단 기준으로 사용하지 않는다.

## 구현과 실험의 확인 범위

- 새 접근 진단은 수치·표정·공개·종료·기억에 연결하지 않았다. 사용자 주장도 일반 배경/서버 사실에 쓰지 않는다.
- 진단 스키마/원문 근거 검증은 형식 검사이며 진실성·분류 의미 검증이 아니다. `reported`를 `correct`나 품질 통과라고 부르지 않는다.
- 기존 의도와 같은 호출을 쓰므로 부가 과제가 의도/출처 분류에 영향을 줄 가능성은 남는다. 기계적으로 수치 경로를 분리했다는 사실이 모델 판단의 독립성을 보장하지는 않는다.
- 초기 실험은 의도 프롬프트+진단 스키마의 예산 초과로 비교 입력 12개가 호출 전에 중단됐다. [초기 실패 원본](../reports/014-approaches-initial-failure.json)을 보존하고 진단 모드의 중복 의도 예시만 줄여 최종 실험을 수행했다. 문맥 한도·추가 호출·재시도 정책은 바꾸지 않았다.
- 이번 결과를 확인한 뒤 수치 연결 여부를 사용자가 결정한다. 이번에는 연결을 구현하지 않았다.
