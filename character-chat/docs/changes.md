## 2026-10-21 — 007 · public-records / 선택식 공개 기록 성공 경로와 서버 결과 표시

### 변경 이유와 이전과 달라진 점

사용자 대화에서 NPC가 미구현 신분증 검증·허가 발급을 완료했다고 말하고 목록은 거절하는 순환이 확인됐다. 기존 테스트는 봉인·수치·저장·회귀를 검증했지만 성공 경로·대사 사실성·해당 연속 대화는 검증하지 않았다. [실패 사례 설명](failure-cases/identity-permit-loop.md), [14회 입력·응답 원문](../tests/fixtures/identity-permit-loop.json)을 보존했다.

변경 전 최신 그림이 [006](architecture-history/006-dialogue-diagnosis.md)과 일치함을 확인했다. 새 버전 archive-2.0은 공개 기록 3개의 고정 이름·본문을 설정에 저장하고, list_records → select_record(record_id) → read_record 경로를 제공한다. progress에 목록 확인·선택 ID·열람 ID 목록을 저장한다. 잘못된 ID·선행 조건 미충족은 서버 실패 결과로 표시한다. 봉인 요청 거절·강제 접근 경고/종료·수치 규칙은 유지한다. 신분증 검증·허가 발급·자연어 행동 해석은 추가하지 않았다.

server_result()가 중요한 완료·거절·종료·다음 진행과 공개 기록을 확정한다. 모델 대사와 별도의 서버 결과 카드에 원문을 표시하고 그 결과도 턴에 저장한다. advance_state()로 예상 상태를 계산해 모델에게 전달하되 생성·독립 검증 성공 전에는 저장하지 않는다. 모델은 원래 대사를 흉내 낼 assistant 예제 대신 JSON 장면 자료를 받고, 과거 NPC 응답은 해당 서버 확정 결과로 대체한다. 초기 인사·서버 결과 없는 구버전 대사는 그대로다. 실제 종료 후에는 가능한 다음 행동을 빈 배열로 전달한다. 생성·연결·수치 오류 시 기존처럼 턴·체크포인트 모두 무저장이다. 유사도 차단·재시도·금지어 필터는 추가하지 않았다.

CHARACTER_CHAT_DEV=true에서 선택 행동·실제 판정 전 상태·서버 결과·생성기 및 실제 HTTP 입력·원본 모델 출력·저장된 최종 상태를 요청별 API/화면 패널에 표시한다. 기본 false이며 DB·기억에 저장하지 않는다. 생성 실패는 미저장과 확보한 원본을 표시하고, 다음 요청·재조회·회귀 때 이전 진단을 지운다. 생성 전 입력·revision 오류에는 진단이 붙지 않는다.

### 남은 문제·현재 범위

모델이 질문을 회피하거나 인사를 반복하고, 고정 원문 시간 정보를 바꾸거나 면담 종료를 보관소 전체 폐쇄로 과장하는 경우가 남았다. 서버 카드는 실제 결과와 원문을 보장하지만 자유 대사의 의미 전체를 자동 검증하지 않는다. 부정 테스트가 거짓 대사를 차단했다는 뜻은 아니며, 그 대사가 화면에 표시될 수도 있다. 자동 상태 통과를 대사 품질 보증으로 해석하지 않는다.

archive-1.0 분기·체크포인트를 자동 마이그레이션하지 않고 기존 이력을 보존한다. 새 공개 경로는 새 게임에서 시작한다. 모델용 새 이력은 서버 결과 중심이므로 과거 모델 대사의 개별 말투·표현을 그대로 기억시키는 방식은 아니다. 선택식 경로의 사용자 직접 플레이 이후에 자유문장 행동 시도 해석을 진행한다.

## 2026-10-21 — 005 · dialogue-repetition / 같은 인사 반복 재현과 보완

### 변경 이유와 로그 확인

사용자의 `안녕 → 안녕` 입력에서 첫 인사 전문이 반복됐다. 실행 중 health는 올바른 `OllamaProvider`와 instruct 모델을 가리켰고 임시 DB에서도 현상이 재현되어, mock 실행이나 잘못된 모델 태그만의 문제가 아니었다. 004의 실제 6사례 검증은 동일한 짧은 인사 연속 입력을 포함하지 않았다.

첨부 로그의 올바른 모델명, GPU 37/37 계층 적재, 문맥 8192, `truncated=0`, 200 추론 응답을 확인했다. 토큰 타입 경고는 보정 후 실행이 계속됐으며 반복의 원인으로 단정하지 않았다. 템플릿 초기화의 thinking 표기만으로 개별 요청 설정을 단정하지도 않았다. GPU·시스템 설정을 변경하거나 모델을 새로 설치하지 않았다.

### 이전과 달라진 점

- 변경 전에 [004-ollama](architecture-history/004-ollama.md)와 최신 문서의 그림 3개 일치를 확인했다. 기존 001~004 스냅샷은 보존한다.
- 캐릭터 시점·인사·잡담 지시를 간소화하고 사용자 발언을 JSON 작업으로 감싸는 대신 자연어 user 메시지와 기존 대화 역할을 유지한다. 핵심 설정·현재 상태·행동 결과는 system 데이터와 Proposal 스키마로 구분한다. 사용자 주장이나 행동을 사실로 확정하지 않는 서버 규칙은 유지한다.
- 같은 발언이 연속된 잡담이면 이전에 답했음을 인지하도록 장면 지시를 추가한다. 모든 질문을 열람 허가 확인으로 끝내지 않도록 안내한다. 기본 temperature는 0.2에서 0.6으로 바꿨다.
- `request_proposal()`이 HTTP·JSON·상태 제안 검증을 담당하고 `propose()`가 `repeated_dialogue()`로 직전 캐릭터 대사와 비교한다. 공백 제거 후 동일하거나, 두 문자열이 각각 24자 이상이고 유사도가 0.88 이상이면 반복으로 판정한다.
- 반복일 때에만 추가 system 지시와 temperature=0.8로 **최대 1회 재생성**한다. 원래 사용자 입력·기억·상태는 바꾸지 않는다. 재생성 결과도 같은 형식·판정·반복 검사를 거치며 실패하면 502, 턴과 자동 체크포인트는 전혀 저장하지 않는다. 연결·형식·상태 오류 자체는 자동 재시도하지 않는다.
- `generation.attempts`를 추가했다. elapsed_ms는 두 호출을 포함한 전체 생성 시간이며 Ollama 자체 통계는 마지막 호출 기준이다. 추가 system 지시 공간도 문맥 예산에 예약한다.
- 실제 모델 검증 스크립트에 동일 인사 2회와 업무 질문을 추가하고, 실패 시에도 실패 보고서를 남기도록 했다. 현재 구조는 [005-dialogue-repetition](architecture-history/005-dialogue-repetition.md)으로 보존한다.

### 검증 결과

- **Python 테스트 60개 통과**. 정확·유사 인사 반복 뒤 재생성 성공 시 revision 1 증가·1턴·1개 체크포인트만 저장함을 확인했다. 두 번째도 반복, 두 번째 호출 타임아웃, 두 번째 제안 수치 오류에서는 상태·대화·revision·체크포인트 무저장을 확인했다.

## 2026-10-21 — 004 · ollama / mock 유지 및 실제 로컬 모델 연결

### 변경 이유

모의 응답으로 확인한 상태·복원 규칙을 유지하면서 실제 로컬 LLM의 대사 생성과 GPU·지연을 학습·검증하기 위해서다. 연결·모델 응답 실패에서도 일부 상태만 저장되면 안 된다.

### 변경 전 확인과 설치 범위

- 현재 코드와 [003-turn-regression](architecture-history/003-turn-regression.md)의 그림 3개가 일치함을 확인했다. 001·002·003은 보존한다. 사용자에게 설명한 모델 후보·크기와 설치 위치를 안내한 뒤 다운로드했다.
- 제한 실행의 NVML 오류와 달리 제한 밖의 읽기 전용 진단에서는 WSL2 `lee`의 RTX 3070 Ti 8GB가 인식됐다. 당시 GPU 메모리는 1,434MiB/8,192MiB였고 로컬 Ollama 명령·서버는 없었다.
- 프로젝트 `.runtime/ollama/`에 공식 배포본 0.40.6, `.runtime/models/`에 모델을 저장했다. 본체 압축 다운로드 약 1.44GB, 해제 후 약 2.2GiB. 모델은 시험용과 최종 후보 각각 약 2.5GB다.
- 최초 서버 실행으로 `~/.ollama`에 키가 생성됐다. 키 내용·모델·실행 파일·임시 보고서는 Git에 포함하지 않는다. sudo·시스템 서비스·드라이버·시스템 Python·WSL 설정·셸 프로필은 변경하지 않았다.

### 이전과 달라진 점

- `Settings.from_env()`와 `make_provider()`로 `mock` 기본값을 유지하면서 `CHARACTER_CHAT_PROVIDER=ollama`를 선택하게 했다. `.env.example`은 예시이며 자동 로딩하지 않는다.
- `OllamaProvider.payload()`·`propose()`를 추가했다. 선택 분기만 입력으로 구성하고 사용자 주장을 미검증 발언으로 구분한다. 상태 변경은 기존 서버 판정을 따른다.
- `/api/chat`의 JSON Schema와 verdict const를 사용하고, 반환 JSON·제안·판정 일치를 독립 검증한다. 연결·타임아웃·HTTP 오류, 큰 응답, 중복 JSON 필드, 미완성·잘못된 출력·수치·문맥 예산 초과를 저장 전에 거부한다.
- `GenerationResult`는 제안과 요청별 시간·모델 통계를 분리한다. 성공 후에만 `generation`을 응답에 추가하고 스냅샷에는 넣지 않는다. health·화면에는 설정 모델명과 성공 요청의 소요 시간을 표시한다.
- 모델 호출은 쓰기 트랜잭션 밖에서 진행하며, 성공 후 revision을 다시 검사하고 턴과 자동 체크포인트를 함께 저장한다. 실패 시 자동 mock 대체·재시도 없이 502를 반환한다. 기존 DB 스키마와 003의 선택 대화 완료 시점 회귀는 유지했다.
- `serve_ollama.sh`는 loopback 전용 수동 실행과 클라우드 비활성화를 설정한다. `verify_ollama.py`는 임시 DB로 실제 모델을 검증한다.

### 모델 선택과 실제 측정

- 후보: Qwen3 4B 계열 약 2.5GB, Qwen3 8B 약 5.2GB, Gemma3 4B 약 3.4GB. 후자의 두 모델은 다운로드·추론하지 않았다. 근거와 실행 방법은 [Ollama 안내](ollama.md)에 있다.
- 최초 `qwen3:4b`는 현재 thinking 모델 태그와 같으며 구조화 대사에서 인사를 반복했다. 프롬프트 보완 후에도 반복이 남아, 비사고형 **`qwen3:4b-instruct-2507-q4_K_M`**를 추가 다운로드해 최종 기본값으로 선택했다. 모델 학습·파인튜닝은 하지 않았다.
- 최종 모델 digest 접두사 `0edcdef34593`, Q4_K_M. `ollama ps` **100% GPU**, context 8192, `/api/ps`의 모델 size와 size_vram은 모두 3,877,571,133바이트 (약 3.9GB). 전체 GPU는 당시 **5,287MiB/8,192MiB** 사용했다.

### 검증 결과

## 2026-10-21 — 003 · turn-regression / 선택 대화까지 남기는 회귀

**변경 유형:** 코드 동작 수정 + 문서 갱신.

### 변경 이유

사용자가 원하는 것은 5번째 입력 후 2번째로 돌아갈 때 **2번째 입력과 답변까지 유지하고 3·4·5번째 이후를 제거하는 회귀**다. 002는 선택한 입력 직전으로 돌아가 선택한 입력도 빠지고 초안으로 채우는 동작이어서 기준 시점이 달랐다.

### 이전과 달라진 점

- 변경 전에 최신 문서와 [002-message-jump](architecture-history/002-message-jump.md)의 Mermaid 3개가 일치함을 확인했다. 기존 001·002 스냅샷은 수정하지 않는다.
- `RegressRequest`와 `POST /api/branches/{branch_id}/regress`의 `regress()`를 추가했다. 선택 대화 번호와 revision을 검증한 뒤 그 대화의 **답변까지 완료된 상태**로 새 분기를 만든다.
- 다음 입력의 직전 체크포인트가 선택 대화의 완료 상태임을 이용한다. 같은 게임인지와 스냅샷의 대화 앞부분 일치를 확인한다. 마지막 턴은 현재 상태를 체크포인트로 보존한다. DB 테이블·컬럼과 매 입력 전 자동 저장 방식은 변경하지 않았다.
- 따라서 002의 기존 자동 체크포인트도 새 회귀 동작에 사용할 수 있다. 과거 상태가 없으면 대화만 잘라 가짜 상태를 만들지 않고 비활성 또는 409로 거부한다.
- 버튼은 **↶ 여기로 회귀**로 바꾸고 `jumpToMessage(turnNumber)`가 새 API를 호출한다. 선택 입력을 초안으로 채우지 않으며 입력창과 행동 선택을 초기화한다. 이후 새 입력은 다음 순서의 대화가 된다.
- 현재 화면에서 선택 턴 이후 대화와 상태가 제거되지만 이전 기록은 원본 분기에 보존한다. 기존 체크포인트 직접 복원 API의 의미는 바꾸지 않았다.
- 화면 대화 횟수는 revision 대신 실제 사용자 메시지 개수로 표시한다. 회귀 후 revision 0이어도 대화 2회로 표시한다.
- 최신 구조 문서·README를 갱신하고 [003-turn-regression](architecture-history/003-turn-regression.md)을 추가했다. 그림의 노드 ID·참여자 순서·흐름 방향은 유지한다.

## 2026-10-21 — 002 · message-jump / 발언 옆에서 다시 시작

**변경 유형:** 코드 동작 변경 + 문서 갱신.

### 변경 이유

별도 체크포인트 저장·복원 패널 대신, 대화의 “당신 · 발언” 옆에서 해당 시점으로 바로 돌아가는 조작을 제공하기 위해서다.

### 이전과 달라진 점

- 변경 전에 최신 구조와 [001-mock](architecture-history/001-mock.md)의 Mermaid 블록 3개 및 현재 mock 저장 경로를 확인했다. 기존 문서의 관리 안내·상대 링크 차이 외에 변경 전 구조는 동일하여 중복 스냅샷을 만들지 않았다. 001 파일은 수정하지 않았다.
- `chat()`이 성공한 턴마다 **전송 직전 전체 상태**를 자동 체크포인트로 저장하고, 새 사용자 메시지 JSON에 `checkpoint_id`를 연결한다. 기존 SQLite 테이블·컬럼을 사용하므로 DB 스키마 마이그레이션은 없다.
- 자동 체크포인트 INSERT와 대화·상태 UPDATE를 같은 쓰기 트랜잭션으로 처리한다. 응답 검증 실패·revision 충돌 시 저장하지 않고, DB 반영 중 오류가 나면 둘 다 롤백한다.
- 사용자 발언 옆 **↶ 여기서 다시 시작**을 누르면 기존 `restore()`로 새 분기를 만든다. 선택한 발언과 그 이후는 새 분기에 포함되지 않으며, 선택한 문장·행동은 수정 가능한 입력 초안으로 채운다. 자동 재전송은 하지 않는다. 종료 후에도 사용할 수 있다.
- 별도 수동 체크포인트 패널과 목록 요청을 제거했다. 보존된 분기 선택 UI와 기존 수동 저장·조회·복원 API 및 과거 데이터는 유지했다.
- 자동 저장 지점이 없는 구버전 발언은 버튼을 비활성화하고 툴팁에 이유를 표시한다. 대화 내용만으로 과거 상태를 재계산하지 않는다.
- `build_context()`에서 UI 메타데이터 `checkpoint_id`를 제외한다. 복원 이후 생성기 입력은 선택 분기의 설정·기억·대화만 사용한다.
- 최신 구조 문서와 README를 갱신하고 [002-message-jump](architecture-history/002-message-jump.md)를 추가했다. 다이어그램은 기존 노드 ID·흐름 방향·참여자 순서를 유지하고 변경된 저장·버튼 동작만 수정했다.

### 검증 결과

- 기존 테스트와 추가 검증을 합쳐 **27개 통과**. 전송 직전 상태 전체 복원, 종료 상태에서 재시작, 원본 분기 보존, 이전 메시지의 복원 링크 유지, 미래 대화·사건·기억 격리, 생성기 입력에서 복원 ID 제외를 확인했다.
- 잘못된 응답과 동시 요청 충돌이 불필요한 자동 저장 지점을 만들지 않는지 확인했다. DB UPDATE 실패를 주입해 체크포인트 INSERT까지 함께 롤백되는지 검증했다.

## 2026-10-21 — 001 · mock 기준선 보존 및 문서·Git 관리 도입

### 이전과 달라진 점

- 이전에는 최신 구조 문서만 있었고, 번호별 구조 스냅샷·이 변경 기록·프로젝트 `AGENTS.md`는 없었다.

- `architecture.md`에 현재 단계와 스냅샷·변경 기록·관리 지침 링크를 추가했다. 다이어그램의 노드 이름·순서·배치 지시·흐름은 변경하지 않았다.
- `AGENTS.md`에 주요 구조 변경 전 보존 확인, 완료 후 다음 번호 스냅샷 추가, 기존 파일 보존, 문서와 코드 동작 변경 구분, 로컬 커밋 규칙을 기록했다. 기존 파일은 없어 새로 만들었다.
- 프로젝트와 상위 경로에 Git 저장소가 확인되지 않아 프로젝트 폴더에 `main` 브랜치의 로컬 저장소를 초기화했다. 기존 이력은 없었으며, 현재 코드·테스트·문서를 최초 기준선으로 함께 커밋한다.
