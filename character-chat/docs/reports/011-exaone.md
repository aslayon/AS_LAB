# 011 · EXAONE 대상 계약과 기본 모델 전환

2026-10-21 (Asia/Seoul). 코드 동작 변경. 유료 API·추가 모델 탐색/다운로드·시스템 설정 변경 없음.

## 원인과 최소 수정

과거 [임시 연결 원문](model-comparison/exaone-game.json)에서 `방문 기록을 선택할게요.`에 `select_record / public`이 출력됐다. 기록 ID/제목은 입력에 있었지만 프롬프트는 정확한 이름 또는 public 등을 나열했고, `IntentProposal.target`은 임의 문자열을 허용했다. 서버의 거절은 정상이며 선택은 실제로 완료되지 않았다.

현재 `intent_context()`는 해당 분기의 제목→ID `selection_targets`를 전달한다. `OllamaProvider.interpret()`는 목록 전체/public과 개별 선택/ID의 차이, 이전 선택과 새 선택의 차이를 설명한다. 현재 분기의 모든 제목→선택 출력 예시를 데이터에서 생성한다. 특정 테스트 문장/모델 이름에 따른 예외는 없다. `intent_schema()`는 행동별 객체 anyOf를 만든다. select_record의 대상은 해당 분기의 실제 ID 열거형만, list_records는 public만, 봉인 행동은 sealed만 허용한다. `validate_intent()`가 응답에도 같은 범위를 검사한다. 잘못된 출력은 기존 502 원자적 오류 경로로 처리하며 치환하지 않는다. 유효 ID라도 입력 이름과 다르면 기존 `ground_intent()`가 실행을 거절한다. 모델이 허용된 ID 중 잘못 고를 가능성은 남는다.

목록·선택·열람/관계 판정·DB·회귀·본문·기억·대사 생성/검토의 규칙과 횟수는 유지했다. 자유 입력 3회(의도/초안/기존 검토), 직접 행동 2회. 문체 금칙어·재생성·추가 검토·후처리 없음.

## 중간 실패도 보존

[모든 실험의 요청·원본 출력·최종 대사](011-exaone-samples.json)는 임시 DB에서 수집했으며 사용자 플레이 데이터가 아니다. 실제 raw/최종과 기존 서버 대체 이유를 구분한다.

1. 첫 수정: 방문/반출입 선택은 성공했지만 보관 분류 안내를 직전 transfer-ledger ID로 출력. 입력과 ID 불일치로 서버가 clarify 처리했다. schema에 포함된 ID라고 올바른 의미는 아니다.
2. 제목→ID 대응과 이전 선택 설명 추가: 보관 분류 안내도 storage-guide로 올바르게 출력. 그러나 여러 기록을 한 분기에서 계속 읽자 6번째 행동의 **초안 호출 전** 기존 문맥 예산 검사에 걸려 502/committed=false. 기존 상태·회귀 구조를 바꾸지 않았다.
3. 각 기록을 독립 게임으로 확인하던 중 보관 분류 안내 선택을 list_records로 잘못 분류. 서버는 실행하지 않았다.
4. 현재 분기에서 만든 제목/행동/ID 예시와 선택 설명을 명확히 한 최종 실행: 아래 14턴 완료. 자동 재생성이나 런타임 재시도가 아니라, 각 코드 수정 후 별도 실험 실행이다. 앞선 출력은 덮어쓰지 않았다.

## 자동 검증과 실제 모델 검증

자동: Python **137개 통과**. 새로운 검사에는 분기별 스키마/제목→ID 입력, 현재 설정과 다른 구버전 ID 사용, 공개 본문 미전달, 잘못된 public/미등록 ID의 502와 상태·체크포인트 무저장, public의 강제 치환 부재, mock 기본값과 Qwen 환경변수 선택이 포함된다. 기존 미래 격리·구버전 분기·설정 보호·3단계 오류 원자성도 실행했다. UI 변경 없어 Node 검사는 이번에 재실행하지 않았다. 기존 Starlette/httpx deprecation 경고 1개가 남는다.

실제 모델: EXAONE 7.8B Q4_K_M, ctx8192/predict512, 의도/검토 temperature0, 초안0.6, 기존 3단계 그대로.

| 경로 | 확인 결과 |
| --- | --- |
| 방문 기록: 목록→선택→열람 | 성공, visitor-log 출력/본문 고정 데이터 |
| 반출입 장부: 목록→선택→열람 | 독립 게임 성공, transfer-ledger |
| 보관 분류 안내: 목록→선택→열람 | 독립 게임 성공, storage-guide |
| 열람 후 2번째 입력으로 회귀 | 선택 완료 상태와 정확히 동일, 열람/본문 이력 없음, 원본 분기 보존 |
| 회귀 후 방금 읽은 내용 질문 | 아직 열람 안 했다고 답함. 의도/초안/검토 입력 모두 미래 본문 미포함 |
| 신분증 주장+봉인 열람 요구 | access_refused, 봉인 유지, 신분증 검증/허가 상태 생성 없음 |
| 봉인 가정 질문 | speak, 강제 접근 횟수 0 |
| 실제 강제 접근 1회/2회 | warning→expelled/ended, 봉인 유지 |

14턴 모두 `resolve()`에 같은 행동/ID를 직접 전달했을 때의 판정과 일치했다. 이것은 서버 판정 비교이며 버튼 UI를 14번 클릭했다는 의미는 아니다. 최종 검증 체크가 모두 true인 것을 확인한 후에만 Settings와 .env.example의 Ollama 기본 모델을 EXAONE으로 변경했다. provider 기본값 mock은 유지했다. Qwen 모델/가중치/기록과 명시적 환경변수 선택은 보존했다. 기존 분기·체크포인트의 설정 데이터는 바꾸지 않으며 모델 자체는 실행 설정을 따른다.

실측 최종 warm 14턴: 전체 3단계 **2.23–2.77초, 중앙값 2.64초**, 단일 초안 중앙값 **1.41초**. 첫 중간 실험의 최초 요청은 모델 로딩 포함 6.00초였다. `/api/ps`에서 size=size_vram=5,734,295,141B, context8192, EXAONE digest c7c4e3d1ca22…를 확인해 전체 GPU 배치를 확인했다. 드라이버 총 VRAM 점유 수치와는 다른 값이다.

## 사람이 읽은 대사 품질: 부분 통과

상태 성공을 대사 전면 통과로 보고하지 않는다. 선택 직후 “모든 방문객의 발자취” 등 미확인 내용을 넓혀 말했고, 회귀 후에도 기록의 일반적인 내용을 추측했다. 봉인 거절에서는 “특별한 절차 없이는”이라고 말해 미지원 절차가 있을 듯한 암시가 남았다. 배경/후속 질문 반복, 수령/클릭 같은 어색한 표현도 있다. 기존 검토는 이런 사례를 놓쳤다.

최종 14턴 중 초안=최종은 12턴이다. 첫 강제 접근은 기존 검토 거절로 서버 문장, 종료는 기존 branch_ended 처리로 서버 문장이 됐다. 이 2건은 **모델 대사 품질 통과가 아니다**. 중요한 결과는 서버 카드/본문이 확정한다. 새로운 문체 장치를 붙이지 않았다.

긴 이력은 기존 UTF-8 바이트 기반 보수적 문맥 예산(8192)에 일찍 걸릴 수 있다. 여러 기록을 같은 분기에서 계속 읽는 긴 경로는 이번에 통과하지 못했으며 독립 게임 3경로와 구분한다. 무저장으로 끝나지만 플레이가 중단되는 한계다. 문맥/기억 최적화는 이번 범위에서 변경하지 않았다. 자연어 분류가 모든 표현에서 맞는다고 보장하지 않는다.
